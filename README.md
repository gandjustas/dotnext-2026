# Модульность без микросервисов

Исходники доклада для DotNext.

## Ветки

**`main`** — код в том виде, в каком он был на докладе. `module-base/` и `modular-analyzer/`
лежат в репозитории как проекты, на которые ссылаются все три демо.

**`fusionmodules`** (эта ветка) — то же самое, но базовый класс, анализаторы и
MSBuild-конвенции подключаются пакетом
[FusionModules](https://www.nuget.org/packages/FusionModules)
([исходники](https://github.com/gandjustas/FusionModules)) вместо вендоренных проектов.

## Что изменилось на этой ветке

- `module-base/` и `modular-analyzer/` удалены; вместо них одна `PackageReference` в каждом
  `Directory.Packages.props`.
- `ModuleBase` переехал в namespace `FusionModules`, поэтому в модулях появился
  `using FusionModules;`.
- `AppContext` в `modular-data` собирает модель из реестра активированных модулей
  (`ModuleBase.GetLoadedModules`), а не из `AppDomain.CurrentDomain.GetAssemblies()`.

Три вещи нашли новые правила анализатора, и все три были настоящими:

- **MOD0007** — `RazorModule` и `MvcModule` регистрировали себя как `IStartupFilter` повторно,
  хотя `ModuleBase` делает это сам. `Configure` выполнялся дважды.
- **MOD0001** — `public readonly record struct AddRequest` в `RemoteRmq`. Прежний анализатор
  проверял только `TypeKind.Class` и структуру пропускал.
- **MOD0008** — `RemoteRmq` регистрирует hosted-сервис. Здесь это намеренно (обработчик RPC
  специально живёт в одном процессе с вызывающим, чтобы померить стоимость круга через RabbitMQ),
  поэтому предупреждение подавлено с объяснением.

Плюс одно исправление, не связанное с пакетом: топология `orders` в `modular-data` не
запускалась. `OrdersMicroservice` использовал `Customer` из `Customers.Entities` как DTO, а
значит зависел от этого модуля, который в этой топологии не загружается. Теперь у него свой
`CustomerDto` — что и есть правильный микросервисный дизайн: сервис, который делит тип сущности
с сервисом, который вызывает, имеет не контракт, а связанность.

## Второй заход: пакет опубликован, версия 0.1.2

Пакет с тех пор подрос и вышел на nuget.org, а примеры подтянуты к тому, что он теперь умеет.
Диагностик новая версия не нашла ни одной (`dotnet build -warnaserror` — ноль предупреждений во
всех трёх демо), а нашлось другое.

**Пакет теперь называется `FusionModules`.** Имя `Modulith` на nuget.org занято чужим пакетом,
да и вокруг слова тесно — `Ardalis.Modulith`, `Productive.Modulith` и ещё пара таких же. Это
успело стоить одной поломки: `NuGet.config` с локальным фидом лежал в корне репозитория, а
контекст сборки образа — папка примера, внутрь он не попадал, и restore, не найдя нужной версии,
молча подставлял чужой пакет — NU1603 в потоке лога — после чего сборка падала стеной CS0246,
которая читается как забытая ссылка. Теперь пакет ставится с nuget.org: ни `NuGet.config`, ни
локального фида, ни правки `Dockerfile` для этого не нужно. Вместе с id переехали namespace и имя
сборки, поэтому в модулях `using FusionModules;`; идентификаторы правил остались прежними —
`MOD0001` и далее.

**Модули переехали на `Microsoft.NET.Sdk`.** Было `Microsoft.NET.Sdk.Web` с
`OutputType=Library` — модуль не веб-приложение, и SDK это знать неоткуда. Мешал переезду
ровно один факт: Web SDK приносил неявные `using`, без которых конвертированный проект
встречает стеной CS0246 на типах, лежащих тут же во фреймворке. Пакет их возвращает сам
(`FusionModules.targets`), так что менять пришлось только строчку SDK. Там, где модуль везёт
`.cshtml` (`MvcModule`, `RazorModule`), теперь `Microsoft.NET.Sdk.Razor`. Побочный эффект:
Visual Studio больше не считает модули запускаемыми веб-проектами и не подкладывает им
`Properties/launchSettings.json` с выдуманным портом.

**`Host.csproj` больше не выставляет `GenerateMvcApplicationPartsAssemblyAttributes`.** Это
делает `FusionModules.targets` для любого проекта, который пакет считает хостом — то самое
MOD0004, только выключенное заранее, а не пойманное потом.

**`HomeController` стал internal** — `AddControllersWithViews().AllowInternalControllers()`.
Публичность контроллера не останавливается на контроллере: публичный тип не может принять
internal-сервис публичным конструктором и вернуть internal-модель публичным действием, так что
следом публичными становятся сервисы, модели и всё, что они называют. Обратный ход дешевле:
MVC-активатор читает `GetConstructors()`, и internal-контроллеру достаточно публичного
конструктора. Razor Pages этого не требовало изначально — `PageModel` в обоих модулях уже был
internal.

**`~/js/razormodule.js` вёл в никуда.** Статика модуля отдаётся из `_content/<AssemblyName>/`,
а ссылка в `Index.cshtml` вела в корень: кнопка «Say hello» не делала ничего, 404 оставался в
консоли браузера. Тест теперь держит обе стороны — и адрес в разметке, и то, что в корне по
этому пути пусто.

**Комментарий про AppDomain исправлен.** Утверждение «показывает и те сборки, на которые
сослались, но которые ни разу не активировали» замером не подтверждается: пока процессом
владеет один хост, фильтр по `HostingStartupAttribute` даёт ровно активированные модули.
Расходится он в другом месте — когда процесс делят несколько хостов, то есть в любой сборке
интеграционных тестов, где загружены модули всех топологий и каждая соберёт объединение.

**Анализаторы, которые терялись вместе с Web SDK.** Переезд на `Microsoft.NET.Sdk` отключал
пять правил, и молча: `StartupAnalyzer` (ASP0000, ASP0001) и MVC1000–MVC1006 лежат не во
фреймворке, а в папке самого Web SDK, и уезжают вместе с ним. Сборка при этом остаётся зелёной —
правила просто перестают спрашивать. Всё, что приходит с `Microsoft.AspNetCore.App.Ref`, работало
и работает, поэтому семейство ASP0xxx про minimal API и маршрутизацию не страдало: модуль сохранял
шестнадцать анализаторов и терял две сборки. Пакет возвращает их с версии 0.1.1 — на примерах
доклада они ничего не находят, но `MvcModule` и `RazorModule` теперь снова под ними.

**Тесты.** `modular-endpoints` проверял одну топологию из трёх; теперь три, потому что
компиляция про internal-контроллер и про адрес статики не говорит ничего — маршрут либо есть в
живом процессе, либо его нет. Семь тестов, включая проверку, что топология без `MvcModule` его
маршрутов не отдаёт, хотя `ProjectReference` на него у хоста есть.

Проверено живьём, а не только сборкой: четыре топологии `load-test` через compose (Local, REST,
gRPC, RabbitMQ), три топологии `modular-data` (monolith, orders, customers) с реальным
PostgreSQL, семь тестов `modular-endpoints`.

## Миграции в `modular-data` зависели от переменной окружения

`dotnet ef` поднимает хост, поэтому `HostingStartup` отрабатывает и модель повторяет
`HOSTINGSTARTUPASSEMBLIES` той оболочки, из которой запустили команду. Замер на этой ветке до
правки: переменная не выставлена — `dotnet ef dbcontext script` выдаёт **ноль таблиц**, и ни
ошибки, ни предупреждения. То есть `migrations add` в чистой оболочке дал бы пустую миграцию, а
существующие миграции в репозитории родились из того, что переменная у кого-то была выставлена.

Теперь у `Web` есть [`DesignTimeDbContextFactory`](modular-data/Web/DesignTimeDbContextFactory.cs),
который называет модули сам. Имена берутся не из массива, написанного руками, — такой массив это
копия `csproj`, которую никто не сверяет, — а из `KnownModules`, который FusionModules генерирует
из ссылок проекта (это ушло в пакет версии 0.1.2). Для `modular-data` получается
`Customers.Entities;CustomersMicroservice;Orders.Entities;Monolith;OrdersMicroservice`:
сначала зависимости, поэтому `Monolith`, который связывает заказы с клиентами, идёт после
обоих модулей сущностей — в том порядке, в каком EF Core применяет конфигурации.

Замер после правки: две таблицы и внешний ключ, который добавляет только `Monolith`, — и то же
самое при `HOSTINGSTARTUPASSEMBLIES=Orders.Entities`. Схема больше не зависит от оболочки.

## Сборка

Ничего особенного: пакет берётся с nuget.org.

```bash
cd modular-endpoints && dotnet build modular-endpoints.slnx
```

Топологии `load-test` и `modular-data` поднимаются своими `docker-compose.yml`.
